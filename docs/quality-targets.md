# 品質目標

この文書は、品質の目標値、根拠、測定方法、実測値、既知の制約をまとめたものです。測定できる目標だけを書き、測定していない項目を達成済みとして書きません。

目標は次の3つに分けて扱います。

```text
外部の基準              WCAG 2.2、Core Web Vitals など、外部で定義された基準
このアプリの品質基準    このアプリがリリースの基準として採用する値
エンジニアリング予算    実測にもとづく、実装上の目安
```

状態（Status）は次のいずれかで書きます。作業中のメモは「根拠・メモ」の欄に書き、Status には書きません。

```text
Pass            目標を満たしている
Fail            目標を満たしていない
Not measured    測定していない
```

目標値のうち「このアプリの品質基準」と「エンジニアリング予算」は、2026-10-15 の実測をもとにした提案です。

## 1. アクセシビリティ

### 1.2 測定方法

2026-10-15 に測定しました。本番ビルド（`npm run build` の後に `npm run preview`）を `http://localhost:4173/taikutsu/` で配信し、Playwright で操作した Chromium で次の4つを確かめました。

- 自動検査: axe-core 4.10.2 の `wcag2a`、`wcag2aa`、`wcag21a`、`wcag21aa`、`wcag22aa`、`best-practice` のルールで検査しました。画面幅 390×844、768×1024、1133×744、1440×900 のそれぞれで、イントロ（表示直後）、戦闘（「たたかう」の後）、ギャラリー（5回攻撃した後）の3つの状態を検査しています。演出が落ち着いた状態を検査するため、動きを減らす設定を有効にしました。
- axe-core が判定を保留した文字のコントラスト比: 背景に疑似要素や画像がある文字は、axe-core が自動判定を保留します（incomplete）。これらの文字については、文字だけを透明にした画面を撮り、文字の各行の範囲の画素から背景色を読み取って、文字色とのコントラスト比を計算しました。画面幅 390×844 と 1440×900 で、上の3つの状態について測定しています。
- 操作できる要素の大きさ: 表示中で操作できる `button`、`a[href]` の表示上の大きさを、上の4つの画面幅と3つの状態で測定しました。ギャラリーの操作の行が枠に収まるかは、画面幅 320、360、390、430、768、1440 px でも確認しています。
- キーボード操作: 画面幅 1440×900 で、Tab キー、矢印キー、Enter キーだけを使い、イントロから戦闘、ギャラリー、「もう一度たたかう」までを操作しました。動きを減らす設定のオンとオフの両方で確認しています。

## 2. パフォーマンス

### 2.1 Lighthouse（このアプリの品質基準）

目標は次のとおりです。

```text
Performance      >= 90
Accessibility    >= 95
Best Practices   >= 95
```

測定の条件は次のとおりです。

- 本番ビルド（`npm run build` の後に `npm run preview`）を `http://localhost:4173/taikutsu/` で配信
- Lighthouse CLI 12.8.2、ヘッドレスの Chrome for Testing、モバイルの設定（`--form-factor=mobile --screenEmulation.mobile --throttling-method=simulate`）
- 対象はアプリを開いた直後（イントロ）の状態
- 3回実行して中央値を報告する（最良の回は選ばない）

2026-10-15 に測定した結果は次のとおりです。

```text
1回目: Performance 97 / Accessibility 100 / Best Practices 100
2回目: Performance 97 / Accessibility 100 / Best Practices 100
3回目: Performance 97 / Accessibility 100 / Best Practices 100
```

| 目標                 | Status | 根拠・メモ                                                                                                    |
| -------------------- | ------ | ------------------------------------------------------------------------------------------------------------- |
| Performance >= 90    | Pass   | 中央値 97（97、97、97）。FCP 1.81〜1.86 s、LCP 2.30〜2.41 s、TBT 0〜1 ms                                      |
| Accessibility >= 95  | Pass   | 中央値 100。Lighthouse はアプリを開いた直後の画面だけを自動判定する。戦闘画面とギャラリーは §1 で検査している |
| Best Practices >= 95 | Pass   | 中央値 100                                                                                                    |

Lighthouse のスコアは測定環境での値（lab data）で、実際の利用者の体験そのものを保証しません。

### 2.3 JS バンドルの予算（エンジニアリング予算）

目標は次のとおりです。

```text
最初に読み込む JS（gzip 後） <= 170 kB
```

根拠: 2026-10-15 の `npm run build` で、ページを開いたときに読み込む JS は、本体（元の大きさ 481.17 kB、gzip 後 155.52 kB）と、チャンクを読み込むための小さなファイル（gzip 後 0.42 kB）の2つでした（Vite の出力）。ギャラリー（gzip 後 128.19 kB、ゲームのデータを含む）と Tone.js（gzip 後 79.42 kB）は別のファイルに分けて、必要になってから読み込みます（§3）。今の構成のまま大きくしないための予算として、実測値に約1割の余裕を持たせた 170 kB を提案します。

| 目標                                  | Status | 根拠・メモ                                      |
| ------------------------------------- | ------ | ----------------------------------------------- |

## 3. 最初の読み込みを軽くするための構成と、その制約

ページは JS が描画するまで何も表示せず、最大の表示要素（LCP）はイントロの区画とその背景の画像です。最初の読み込みを軽くするため、次の3つの構成にしています。

- **Tone.js は効果音をオンにしたときに読み込みます。** Tone.js は読み込まれた時点で音声の処理の準備（AudioContext の作成など）をするため、ページを開いた直後に読み込むと長いタスクになります。2026-10-15 の測定では、最初の JS に含めると Lighthouse の TBT が約 300 ms になりました。
- **ギャラリーは、戦闘が始まったときに裏で読み込みます。** ギャラリーには推薦用のゲームのデータ（JS の元の大きさで約 360 kB）が含まれ、撃破の後にしか使いません。撃破の後の画面遷移は、破片を見せる時間（約0.8秒）とギャラリーの読み込みの両方が終わってから始まります。
- **背景の画像は、線画をグレースケールの4階調に減らした可逆圧縮の WebP です。** 横並びのレイアウトでは幅 1400px（166 kB）、縦積みのレイアウトでは幅 1000px（84 kB）の画像を読み込みます。画像は CSS の背景で、JS がイントロを描画してから読み込みが始まるため、画像の大きさがそのまま LCP に影響します。`<link rel="preload">` で先読みさせても、JS と通信の帯域を分け合うため LCP は変わりません（2026-10-15 の測定）。そのため、先読みは使っていません。

この構成には、次の制約があります。

- **ギャラリーを読み込めなかったときは、ページの再読み込みが必要です。** 通信が切れていたり、再デプロイでファイル名が変わっていたりしてギャラリーを読み込めないと、ギャラリーの代わりにエラーを表示します（[UX仕様](./ux-spec) §6）。ブラウザは一度読み込みに失敗したモジュールをそのページの間は読み込み直さないため、再試行のボタンは置かず、ページの再読み込みを案内しています。
- **通信が遅いと、撃破の後の画面遷移が遅れます。** ギャラリーの読み込みが終わるまで、破片を表示したまま待ちます。
- **効果音をオンにした直後は、音が遅れて鳴ることがあります。** オンにした時点で Tone.js の読み込みを始め、読み込みが終わるまでの操作の音は、読み込みが終わってから鳴ります。

実機のスマートフォンとタブレットでの操作、Safari と Firefox での表示、スクリーンリーダーでの実際の読み上げ、効果音が実際に鳴ることは確認していません。画面サイズごとの表示は、Chromium で画面サイズを指定して確認しています。
