# 品質目標

この文書は、品質の目標値、根拠、測定方法、実測値、既知の制約をまとめたものです。測定できる目標だけを書き、測定していない項目を達成済みとして書きません。

目標は次の3つに分けて扱います。

```text
外部の基準              — WCAG 2.2、Core Web Vitals など、外部で定義された基準
このアプリの品質基準     — このアプリがリリースの基準として採用する値
エンジニアリング予算     — 実測にもとづく、実装上の目安
```

状態（Status）は次のいずれかで書きます。作業中のメモは「根拠・メモ」の欄に書き、Status には書きません。

```text
Pass            目標を満たしている
Fail            目標を満たしていない
Not measured    測定していない
```

目標値のうち「このアプリの品質基準」と「エンジニアリング予算」は、2026-10-15 の実測をもとにした提案です。

### 1.2 測定方法

2026-10-15 に測定しました。本番ビルド（`npm run build` の後に `npm run preview`）を `http://localhost:4173/taikutsu/` で配信し、Playwright で操作した Chromium で次の4つを確かめました。

- 自動検査: axe-core 4.10.2 の `wcag2a`、`wcag2aa`、`wcag21a`、`wcag21aa`、`wcag22aa`、`best-practice` のルールで検査しました。画面幅 390×844、768×1024、1133×744、1440×900 のそれぞれで、イントロ（表示直後）、戦闘（「たたかう」の後）、ギャラリー（5回攻撃した後）の3つの状態を検査しています。演出が落ち着いた状態を検査するため、動きを減らす設定を有効にしました。
- axe-core が判定を保留した文字のコントラスト比: 背景に疑似要素や画像がある文字は、axe-core が自動判定を保留します（incomplete）。これらの文字は、文字だけを透明にした画面を撮り、文字の各行の範囲の画素から背景色を読み取って、文字色とのコントラスト比を計算しました。画面幅 390×844 と 1440×900 で、上の3つの状態について測定しています。
- 操作できる要素の大きさ: 表示中で操作できる `button`、`a[href]` の表示上の大きさを、上の4つの画面幅と3つの状態で測定しました。ギャラリーの操作の行が枠に収まるかは、画面幅 320、360、390、430、768、1440 px でも確認しています。
- キーボード操作: 画面幅 1440×900 で、Tab キー、矢印キー、Enter キーだけを使い、イントロから戦闘、ギャラリー、「もう一度たたかう」までを操作しました。動きを減らす設定のオンとオフの両方で確認しています。

## 2. パフォーマンス

### 2.1 Lighthouse（このアプリの品質基準）

目標は次のとおりです。

```text
Performance      >= 90
Accessibility    >= 95
Best Practices   >= 95
```

測定の条件は次のとおりです。

- 本番ビルド（`npm run build` の後に `npm run preview`）を `http://localhost:4173/taikutsu/` で配信
- Lighthouse CLI 12.8.2、ヘッドレスの Chrome for Testing、モバイルの設定（`--form-factor=mobile --screenEmulation.mobile --throttling-method=simulate`）
- 対象はアプリを開いた直後（イントロ）の状態
- 3回実行して中央値を報告する（最良の回は選ばない）

2026-10-15 に測定した結果は次のとおりです。

```text
1回目: Performance 71 / Accessibility 100 / Best Practices 100
2回目: Performance 72 / Accessibility 100 / Best Practices 100
3回目: Performance 73 / Accessibility 100 / Best Practices 100
```

| 目標                 | Status | 根拠・メモ                                                                                                    |
| -------------------- | ------ | ------------------------------------------------------------------------------------------------------------- |
| Performance >= 90    | Fail   | 中央値 72（71、72、73）。原因は §3                                                                            |
| Accessibility >= 95  | Pass   | 中央値 100。Lighthouse はアプリを開いた直後の画面だけを自動判定する。戦闘画面とギャラリーは §1 で検査している |
| Best Practices >= 95 | Pass   | 中央値 100                                                                                                    |

Lighthouse のスコアは測定環境での値（lab data）で、実際の利用者の体験そのものを保証しません。

### 2.3 JS バンドルの予算（エンジニアリング予算）

目標は次のとおりです。

```text
最初に読み込む JS（gzip 後） <= 350 kB
```

根拠: 2026-10-15 の `npm run build` で、JS は1つのチャンクで、元の大きさ 1,132.97 kB、gzip 後 341.28 kB（Vite の出力）でした。このうち、同梱しているゲームのデータ `data/gameIntros.json` は、単体で gzip すると約 108 KiB です。今の構成のまま大きくしないための予算として、実測値にわずかな余裕を持たせた 350 kB を提案します。

| 目標                                  | Status | 根拠・メモ                                      |
| ------------------------------------- | ------ | ----------------------------------------------- |

## 3. 既知の制約

### Performance が目標に届かない原因

2026-10-15 に、原因を切り分けるための測定をしました。下の表の「取り除いたもの」以外は比較の基準と同じ内容のビルド（測定専用で、公開はしていない）を作り、§2.1 と同じ条件で3回ずつ測った中央値です。最初に読み込む JS は、Lighthouse が記録した転送量です。

| 取り除いたもの                                             | Performance | FCP    | LCP    | TBT    | 最初に読み込む JS |
| ---------------------------------------------------------- | ----------- | ------ | ------ | ------ | ----------------- |
| なし（比較の基準）                                         | 71          | 2.60 s | 4.96 s | 325 ms | 332 kB            |
| ゲームのデータ（10件だけ残す）                             | 67          | 2.23 s | 4.54 s | 600 ms | 229 kB            |
| Tone.js（何もしない代わりのモジュールに置き換える）        | 81          | 2.26 s | 4.67 s | 3 ms   | 275 kB            |
| ゲームのデータと Tone.js                                   | 86          | 1.82 s | 4.08 s | 1 ms   | 172 kB            |
| 背景の画像（44 バイトの画像に置き換える）                  | 87          | 2.58 s | 3.05 s | 211 ms | 332 kB            |
| ゲームのデータ、Tone.js、背景の画像                        | 98          | 1.82 s | 1.99 s | 0 ms   | 172 kB            |
| なし（背景の画像を `<link rel="preload">` で先読みさせる） | 71          | 2.57 s | 4.97 s | 307 ms | 332 kB            |

この結果から、原因は次の3つです。

- **TBT は Tone.js から来ています。** Tone.js を置き換えると、TBT は 325 ms から 3 ms になります。Tone.js は読み込まれた時点で音声の処理の準備（AudioContext の作成など）をするため、ページを開いた直後に長いタスクができます。効果音は初期状態でオフなので、この準備はページを開いた時点では使われていません。ゲームのデータを減らしても TBT は下がりません。
- **LCP は背景の画像の表示を待っています。** LCP の要素はイントロの区画で、その背景の画像（WebP、1400×1120、404 kB）が表示されるまで LCP が確定しません。画像は CSS の背景で、JS がイントロを描画してから読み込みが始まるため、JS のダウンロードと実行のあとに画像のダウンロードが続きます。画像を置き換えると LCP は 4.96 s から 3.05 s になります。先読みさせても、JS と通信の帯域を分け合うため LCP は変わりません。
- **FCP は最初に読み込む JS の大きさで決まっています。** ページは JS が描画するまで何も表示しません。最初の JS には、ギャラリーでしか使わないゲームのデータ（JS の元の大きさの約33%）と、効果音をオンにしたときだけ使う Tone.js（関連するライブラリを含めて約20%）が含まれています。両方を取り除くと、JS の転送量は 332 kB から 172 kB に、FCP は 2.60 s から 1.82 s になります。

### バンドルサイズ

JS が1つのチャンクで、元の大きさが 500 kB を超えるため、ビルドのたびに Vite が警告を出します。ギャラリーとゲームのデータを後から読み込む形にすれば最初の読み込みは軽くなりますが、撃破後に通信することになり、通信に失敗したときの表示も新たに必要になります。

### `AudioContext` の警告

Tone.js が読み込み時に AudioContext を作るため、ブラウザの開発者ツールに「ユーザーの操作の前には開始できない」という警告が2件出ます。効果音はユーザーの操作の後に `Tone.start()` で開始するので、動作には影響しません。原因は、上の TBT と同じ Tone.js の読み込み時の処理です。

### 確認していない環境

実機のスマートフォンとタブレットでの操作、Safari と Firefox での表示、スクリーンリーダーでの実際の読み上げ、効果音が実際に鳴ることは確認していません。画面サイズごとの表示は、Chromium で画面サイズを指定して確認しています。
