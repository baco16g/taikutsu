# 開発の進め方

この文書は、「退屈を、たおせ！」がどのような着想から企画され、どのように開発を進めたかをまとめたものです。何を作るかは [プロダクト仕様](./product-spec) と [UX仕様](./ux-spec)、実装の構成は [アーキテクチャ](./architecture) を参照してください。

## 1. 企画の原点

企画の原点は、あるゲーム販売サイトで「目的はあなた次第」のような、遊ぶ人の体験を表したユニークなタグを見つけたことです。

「アクション」「RPG」「シミュレーション」といった一般的なジャンルの分類ではなく、ゲームを通じて得られる体験を言葉にしている点に興味を持ちました。こうしたタグを活用すれば、遊ぶ人がこれまで知らなかったゲームに出会える、新しい体験を作れるのではないかと考えました。

## 2. 企画の検討

この着想から、ゲームかるたや、インタラクティブなゲーム紹介など、複数の企画を検討しました。最終的に RPG のコマンドバトルを採用した理由は、次の3つです。

1. RPG の戦闘は多くの人にとって親しみやすく、直感的に楽しめること。
2. コマンドを選び、その結果が返ってくるというやり取りが、遊ぶ人に興味を選んでもらう仕組みと自然に結びつくこと。
3. 制作者自身が RPG というジャンルを好きで、その魅力を生かした体験を作りたかったこと。

企画の初期には、友達と一緒にゲームを見つける体験も検討しました。「子どもは自分一人の好みだけでなく、友達と一緒に遊べるかどうかも重視してゲームを選ぶのではないか」という仮説があったためです。この仮説は、ユーザー調査で確かめたものではありません。複数の端末をつないで、友達どうしでゲームかるたを楽しんだり、気になったゲームを相手の画面に送ったりするアイデアを検討しましたが、最終的には一人でも完結できるゲーム発見の体験を採用しました。

## 3. プロトタイプで体験を確かめる

初期段階では、ChatGPT の画像生成機能で作ったコンセプトアートを使って、ビジュアルと世界観を検討しました。イントロ、戦闘、タ・イクツの表現、画面遷移、ゲームギャラリーは、それぞれ個別に検討・試作しました。プロトタイプは Codex などを使って作り、実際の動きを確かめながら体験を検討しました。その後、Claude Code を中心に実装と統合を進めました。

表現の手段としては WebGL や GLSL も検討しましたが、操作性、視認性、実装の保守性などを考え、HTML / CSS / SVG と GSAP を中心とした構成を採用しました。タ・イクツも SVG で描いています。

開発では、プロトタイプを実際に確かめ、体験の目的に照らし合わせて設計と実装を判断することを重視しました。

## 4. データの作り方と推薦の仕組み

### 4.1 データの作り方

ゲームの情報は、外部のゲーム販売サイトからスクレイピングで収集しました。対象が膨大になりすぎないよう、特定のプラットフォームに対応するソフトに限っています。

収集したゲームの紹介文と既存のタグをもとに、それぞれの作品で得られるゲーム体験を抽出・分類しました。その際は、単純なジャンルの分類ではなく、ジャンルを横断して共通するゲーム体験を見つけることを重視しました。たとえば、アクションゲームとアドベンチャーゲームでも、「敵に見つからずに進む」という共通の体験があれば、同じカテゴリに分類できるようにしています。

次の工程は、すべて Claude Code に任せました。

1. ゲームの紹介文と既存のタグからの、ゲーム体験の抽出
2. 体験カテゴリの候補の生成と評価
3. ゲームと体験カテゴリの関連付け
4. 分類結果の品質の検証
5. 検出された問題の修正
6. 推薦が成り立つかどうかの検証

分類結果を人が手作業で確認することはしていません。データは Claude Code による自動の分析と検証を中心に作っています。そのため、ゲームとスキルの結びつきに、人が見れば違和感のある組み合わせが含まれている可能性があります。

### 4.2 データの構造

アプリが読み込むデータは、次の2ファイルです（どちらも `src/catalog/` から読み込みます）。

| ファイル                 | 内容                                                                                                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data/specialMoves.json` | スキル（体験カテゴリ）の一覧。各スキルは `id`、名前（`name`）、説明（`shortDescription`）を持つ                                                                                 |
| `data/gameIntros.json`   | ゲームの一覧。各ゲームは `id`、名前、販売ページの URL（`sourceUrl`）、画像の URL（`thumbnail.remoteUrl`）、キャッチコピー、紹介文と、スキルとの結びつき（`relatedMoves`）を持つ |

`relatedMoves` は、そのゲームが結びつくスキルの `moveId` と、結びつきの強さ（`relevance`。`strong` か `medium`）の組の一覧です。

現在のデータの規模は次のとおりです。

| 項目                                       | 値                                                   |
| ------------------------------------------ | ---------------------------------------------------- |
| スキル                                     | 27種類                                               |
| ゲーム                                     | 399件                                                |
| 結びつき                                   | strong が575件、medium が434件（1作品あたり1〜10件） |
| 1つのスキルと strong で結びつくゲーム      | スキルごとに4〜58件                                  |
| どのスキルとも strong で結びつかないゲーム | 77件                                                 |

### 4.3 推薦の仕組み

推薦（`src/features/gallery/lib/recommend.ts` の `recommendGames`）は、戦闘で選んだ5つのスキルから、ギャラリーに表示する10作品を決めます。判断に使うのは `relevance` が `strong` の結びつきだけです。

1. **strong-tie 枠（最大5作品）**: 選んだスキルと strong で結びつくゲームを選びます。スキルを順番に回し、1周につき各スキルから1作品ずつ選ぶので、結びつくゲームの多いスキルが枠を独占しません。すでに選んだゲームは選びません。
2. **discovery 枠（残り）**: 選んだどのスキルとも strong で結びつかないゲームから選びます。普段は選ばない作品と出会うきっかけにするための枠です。strong-tie 枠が5作品に届かなかった分も、この枠で埋めます。
3. 2つの枠の候補を合わせても10作品に届かない場合は、残りのゲームから補います。

候補を選ぶ順番は、選んだスキルの集合から作ったシード（重複を除いて並べ替えた id から計算する値）をもとにした乱数で決めます。そのため、同じ5つのスキルを選べば、選んだ順番に関係なく同じ10作品が同じ並びで出ます。選ぶスキルの組み合わせが変わると、表示されるゲームも変わります。

ギャラリーで作品の説明に表示する「このゲームで楽しめること」は、そのゲームと strong で結びつく、選んだスキルの説明（`shortDescription`）です。作品ごとに文章を新しく作ることはしていません。

## 5. デザインの参考

実際の表現の検討では、次の3つのデモを参考にしました。参考にしたのは表現の考え方で、現在の実装はアプリの要件に合わせて組み立てています。

### Organic Shape Animations

<https://tympanus.net/Development/OrganicShapeAnimations/>

タ・イクツの有機的な形の変化とアニメーションの参考にしました。現在の実装では、タ・イクツの輪郭を角度の決まった14個の点で表し、点どうしをなめらかな曲線でつないだ SVG のパスとして描いています。HP の段階ごとに各点の中心からの距離を決めておき、被弾のたびにその距離を補間して形を変えます。攻撃を受けていない間は、時間に応じて各点の距離をわずかに揺らし、呼吸しているような動きを出しています（`src/features/taikutsu/`）。

### Multi-Layer Page Reveal

<https://tympanus.net/Tutorials/PageRevealEffects/>

戦闘画面からゲームギャラリーへ移る画面遷移の参考にしました。現在の実装では、3枚のシートが少しずつ時間をずらして右下から左上へ斜めに画面を覆い、覆った裏でギャラリーへ切り替えてから、同じ向きに外れていきます（`src/features/reveal/components/RevealTransition.tsx`）。

### On-Scroll 3D Carousel

<https://tympanus.net/Development/3DCarousel/>

ゲームギャラリーの立体的なカードの配置と操作の参考にしました。現在の実装では、正面の作品からの距離に応じて、各カードの横の位置・奥行き・傾き・大きさ・不透明度を決め、輪のように並べています。作品の切り替えは、スクロールではなく、矢印ボタン、点、スワイプ、キーボードの左右の矢印キーで行います（`src/features/gallery/`）。

## 6. 変更時のチェック

変更を確定する前に、次のコマンドがすべて通ることを確かめます。GitHub Actions のデプロイでも、このうち `npm run build` と `npm run docs:build` を実行します。

```text
npm run lint
npm test
npm run build
npm run format:check
npm run docs:build
```

`npm run build` は型チェック（`tsc -b`）を含みます。テストでは、純粋なロジック（山札、推薦、形の計算、進行段階のルールなど）に加えて、スキル一覧とギャラリーの操作の決まり（キーボードのフォーカスの移り方を含む）、イントロからギャラリーまでの通しの流れ、ギャラリーを読み込めなかったときの表示を確かめています。品質の目標と実測値は [品質目標](./quality-targets) を参照してください。
